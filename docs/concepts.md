# Core concepts

This guide explains the user-facing model behind zero-migrate. For the fastest
path to a working migration, start with [Getting started](getting-started.md).

## Write once, choose the target at deployment time

A migration is an ordinary TypeScript module that describes database changes
with the `zero-migrate` API:

```ts
import { ids, table, t } from "zero-migrate";

export const name = "create_accounts";

export default {
  schema() {
    table("accounts").create({
      columns: {
        id: ids.typeId({ prefix: "acct" }).primaryKey(),
        email: t.string({ length: 254 }).notNull(),
      },
    });
  },
};
```

The default export has one forward phase. Use `schema()` for DDL only. Use
`data()` for DML and declare exactly one rollback disposition: a recorded
`inverse()` or a non-empty `irreversible` reason. For example, a reversible data
migration is:

```ts
import { table } from "zero-migrate";

export const name = "seed_starter_plan";

export default {
  data() {
    table("plans").insert({
      rows: { id: "starter", price_cents: 0 },
    });
  },
  inverse() {
    table("plans").delete({
      where: (column) => column("id").eq("starter"),
    });
  },
};
```

When no truthful reverse exists, say why:

```ts
import { table } from "zero-migrate";

export const name = "purge_expired_sessions";

export default {
  data() {
    table("sessions").delete({
      where: (column) =>
        column("expires_at").lt("2026-01-01T00:00:00Z"),
    });
  },
  irreversible: "the deleted session rows cannot be reconstructed",
};
```

DDL and DML cannot share a module. This is enforced from the operations the
callbacks record: DML inside `schema()` and DDL inside `data()` are both
refused. `up()` and `down()` are gone; neither is deprecated or accepted as an
alias.

The same module can be validated for PostgreSQL, MySQL 8, or SQLite. It is
portable only when every operation it uses is supported by the selected target.
When database-specific behavior is intentional, use `dialect()` to describe the
alternatives explicitly.

See [Choosing a database target](dialects.md) for the exact support matrix.

## A migration is a reviewable document

Recording a migration's forward `schema()` or `data()` phase produces a
structured migration document. It describes the requested schema or data
operations without opening a database connection. A reversible data migration's
`inverse()` is recorded independently rather than inferred from its forward
operations.

Use `lint --explain` to inspect that document and its rendered SQL without a
database connection:

```bash
zero-migrate lint --dir ./migrations --explain
```

Preview and rendered SQL are useful for code review, but neither simulates the
live database.

## Migration modules are trusted code

The Node API and CLI import migration modules as ordinary JavaScript. They do
not sandbox the module, so its top-level code and `schema()`, `data()`, or
`inverse()` callbacks have the same process access as the host running
zero-migrate.

Run only trusted modules directly. If migrations are generated by users or AI,
evaluate them in a separate sandbox with no secrets, network access, filesystem
authority, or database credentials. Use a reviewed Rust/custom-host workflow to
move the approved migration into deployment.

## Author, host, and operator responsibilities

zero-migrate keeps three responsibilities distinct:

1. The **author** describes the database change in TypeScript.
2. The **host** supplies the application identity, project schema, target
   database, and ownership information.
3. The **operator** controls credentials, database privileges, approvals,
   deployment order, backups, and incident recovery.

One person may fill all three roles in a small project. The distinction matters
when a platform runs migrations for multiple applications or customers.

The migration module does not choose its database credentials, authoritative
owner, project schema, approval, or audit actor.

## Names and ordering

Give every migration a unique, stable, descriptive name:

```ts
export const name = "add_account_status";
```

The CLI discovers `.ts`, `.mts`, `.cts`, `.js`, `.mjs`, and `.cjs` files,
ignores `.d.ts` files, and processes filenames in lexicographic order. Timestamp
prefixes therefore produce a predictable sequence:

```text
20260715090000_create_accounts.ts
20260715103000_add_account_status.ts
20260716081500_add_account_status_index.ts
```

The deploying application identity and migration name form durable migration
identity. Do not reuse a name, and after apply do not rename the migration or
change its contents. Create a new, uniquely named forward migration instead.

## Validate, plan, preview, and apply

These commands answer different questions.

### Preview

Preview shows the structured operations produced by a migration module. It does
not connect to a database. Reach it with `lint --explain` (CLI) or the Node
preview API.

### Validate

JavaScript `validate()` checks that the migration is well formed, supported by
the selected dialect, confined to the supplied project schema, and allowed by
the supplied table ownership registry. It does not inspect the live database.

### Plan

JavaScript `plan()` returns the same offline validation result together with the
migration document for review. It does not render SQL, detect live schema
differences, or classify every apply-time database condition.

### Apply

Apply adds the trusted host inputs, performs the target-specific safety checks,
acquires the project lock, checks migration history, executes pending work, and
records the result.

PostgreSQL and MySQL apply read the current target catalog before preparing work
that depends on existing tables, columns, or indexes. This catalog-aware step is
not a complete structural-drift comparison or a database-backed dry run.

The public Node API and CLI execute DDL from `schema()` modules and `insert`,
`update`, `delete`, and `backfill` from separate `data()` modules on PostgreSQL
and MySQL 8. Calls within a phase execute in authored order. SQLite executes the
same operation set and is a Node, CLI, and Rust target.

Pending deletes and backfills require explicit operator approval. Backfills also
require an exact ordered, non-null primary or unique candidate-key tuple plus an
explicit cursor-stability mode. Under the project lock, apply checks every pending approval-gated step
in the complete plan before the first authored step executes. A later
unapproved delete or backfill cannot follow an earlier step from that plan.

A backfill captures a fixed terminal cursor before its first batch. Each batch
saves the last committed cursor, and retries stop at that original boundary.
The bounded cohort does not cover concurrent inserts by itself: before capture,
new rows must be made to fail the filter, or a final catch-up must run while
writes are stopped. MySQL data targets must be trigger-free InnoDB tables. SQLite
backfills additionally require declared `INTEGER` or `TEXT` affinity with
consistently typed live cursor values. PostgreSQL and SQLite backfills reject
pre-existing enabled user triggers; the managed PostgreSQL online rename
workflow remains supported.

### PostgreSQL online column rename

PostgreSQL column rename separates database preparation from application
cutover. The migration still contains one `.column(source).rename({ to, type })`
operation, but the approved first apply returns a pending contract instead of
dropping the source immediately.

That rename must be the only operation in the PostgreSQL migration that targets
its table. Operations on different tables may remain. Put every other operation
on the renamed table in a later migration and apply it only after resolution.

The source must exist, the destination must not exist, and the declared type
must match the source's live PostgreSQL type. The table must use `id` as its
complete, non-null, single-column primary key with a supported orderable cursor
type, no pre-existing enabled user triggers, and row-level policy that permits
the selected updates. Existing values are copied before the pending contract is
returned.

During the coexistence window, deploy application code that uses the
destination and wait for all older instances and consumers to stop using the
source. Other migration changes to that table are blocked. Then explicitly
resolve the returned `pendingVersion`: apply keeps the destination and drops the
source; abort keeps the source and drops the destination. Both resolutions
require approval.

Writes through either name keep the values aligned during coexistence; if both
receive different values in one statement, the destination wins. The
destination is nullable but otherwise keeps the source's exact live PostgreSQL
type, including modifiers. Equivalent built-in aliases are accepted without
discarding modifiers; modifier drift is refused during resolution. Defaults,
constraints, indexes, comments, and dependent objects need separate review and
follow-up migrations after resolution. Source dependencies can block
resolution and must be audited before rollout.

An unchanged retry skips completed work and resumes an interrupted backfill. A
pending contract remains pending across repeat apply calls until Node
`resolvePending()` or CLI `resolve <migration> --commit|--rollback` resolves it.
Resolution cleanup is
all-or-nothing: a failure leaves both columns and the managed rename trigger
intact, keeps the contract pending, and keeps the table blocked.

After apply or abort resolution succeeds, the original rename identity is
terminal and exact replay does not open another contract. To try again after an
abort, author a new migration with a new exported name. An aborted plan does not
satisfy `dependsOn`, so dependent work remains blocked until it points to a new
replacement migration. See
[Operating migrations](operations.md#postgresql-online-column-rename).

## Project identity and ownership

The main host inputs are:

- `ownerApp`: the trusted identity of the application deploying the migration;
- `projectSchema`: the SQL namespace owned by that application;
- `registry`: a map from existing table names to their trusted owners.

For example:

```ts
const registry = {
  accounts: "app_identity",
  orders: "app_orders",
};
```

A migration can create and then alter a table in the same module without a
registry entry. A later migration that alters the existing table needs a
matching entry. Missing or mismatched ownership fails closed.

`projectSchema` is a confinement boundary, not a provisioning request. Create
the schema or database before applying the migration.

## Policy and approval

Policy controls which capabilities a migration may use, including destructive
changes, raw SQL, cross-schema access, roles, extensions, and optional required
table shape.

The public Node API requires a non-empty ordered table-shape `policy`
array for database verbs. The first entry is the trusted root/bound and later
entries may only narrow it. The CLI accepts the same stack through repeatable
`--policy` flags. Platforms that need broader custom policy can make
those decisions in a Rust host, but arbitrary executor policy is not available
to the public apply API yet.

Pending destructive work and backfills require explicit operator approval. The
Node API uses `approved: true`; the CLI uses `--approve`. Approval should always
be bound to the exact migration content that was reviewed.

See [Policy model](policy.md) and [Security model](security-model.md).

## The migration journal

Every executable step has a stable journal identity, and completed work adds an
event to an append-only journal. The journal captures the complete migration
checksum, including bound data values, together with the actor and time so
zero-migrate can:

- detect changed content for an already-known migration;
- reconcile PostgreSQL and MySQL migration status;
- prevent unsafe reapplication;
- resume backfills after interruption and expose non-transactional recovery
  state for reviewed repair.

Pass the ordered migration set to Node `status()` for plan-aware PostgreSQL or
MySQL status. The CLI does this from `--dir` automatically. Status includes all
schema and data steps and distinguishes applied, aborted, pending, partial,
drifted, and blocked migrations. Top-level `aborted` contains terminal aborted
plan IDs, separate from `applied` and `pending`; `rolledBack` identifies versions
whose latest journal event is `rolled_back`. JavaScript `history()` remains
PostgreSQL-only.

Status also exposes outstanding rename obligations in `pendingContracts`,
plans waiting on them in `blocked`, and journal identities missing from the
supplied set in `unexpectedJournal`. These are operator-visible states, not work
that apply silently discards.

## Transactions and partial completion

A directory of migration files is not one global transaction. If an earlier
migration succeeds and a later one fails, the earlier migration remains
applied.

PostgreSQL and SQLite can commit supported transactional schema or ordinary data
work together with its journal event. MySQL ordinary data statements are
transactional, but MySQL DDL auto-commits, so interrupted schema work uses
recovery state and stops for operator repair instead of replaying ambiguous DDL.
Backfills on every target
commit bounded batches and save their cursor so an interrupted run can resume
within its previously captured terminal boundary. Runtime database errors can
still leave earlier completed steps applied after execution begins.

## Drift and rollback

Apply detects changed migration content through journal checks. Structural drift
between the expected and live schema is a separate, explicit Rust workflow; it
is not checked automatically by JavaScript apply.

Node and CLI rollback can unwind an eligible `data()` migration by running the
author's recorded `inverse()`. The inverse is lowered through the same guarded
IR authoring path as forward operations and executed as parameterized DML on
PostgreSQL, MySQL, and SQLite. Its DML and `rolled_back` journal event commit
together. Plan-aware status then reports the plan pending, and a later apply
replays its forward `data()` phase.

Reversibility has two hard limits: the forward plan must lower to exactly one
journaled step, and `inverse()` must lower only to transactional DML. Rollback
refuses a plan outside either limit before execution. It also refuses a data
migration declared `irreversible` and reports the author's reason. Keep tested
backups and prefer a reviewed forward fix when those constraints do not fit the
incident.
