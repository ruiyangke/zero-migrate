# Core concepts

This guide explains the user-facing model behind zero-migrate. For the fastest
path to a working migration, start with [Getting started](getting-started.md).

## Write once, choose the target at deployment time

A migration is an ordinary TypeScript module that describes database changes
with the `zero-migrate` API:

```ts
import { table, t } from "zero-migrate";

export const name = "create_accounts";

export default {
  up() {
    table("accounts").create({
      columns: {
        id: t.id({ prefix: "acct" }),
        email: t.text().notNull(),
      },
    });
  },
};
```

The same module can be validated for PostgreSQL, MySQL 8, or SQLite. It is
portable only when every operation it uses is supported by the selected target.
When database-specific behavior is intentional, use `dialect()` to describe the
alternatives explicitly.

See [Choosing a database target](dialects.md) for the exact support matrix.

## A migration is a reviewable document

Running a migration's `up()` function produces a structured migration document.
It describes the requested tables, columns, indexes, constraints, views, and
other operations without opening a database connection.

Use preview to inspect that document:

```bash
zero-migrate preview --dir ./migrations
```

Preview is useful for code review, but it is not rendered SQL and does not
simulate the live database.

## Migration modules are trusted code

The Node API and CLI import migration modules as ordinary JavaScript. They do
not sandbox the module, so its top-level code and `up()` function have the same
process access as the host running zero-migrate.

Run only trusted modules directly. If migrations are generated by users or AI,
evaluate them in a separate sandbox with no secrets, network access, filesystem
authority, or database credentials. Use a reviewed Rust/custom-host workflow to
move the approved migration into deployment.

## Author, host, and operator responsibilities

zero-migrate keeps three responsibilities distinct:

1. The **author** describes the database change in TypeScript.
2. The **host** supplies the application identity, project schema, target
   database, and ownership information.
3. The **operator** controls credentials, database privileges, approvals,
   deployment order, backups, and incident recovery.

One person may fill all three roles in a small project. The distinction matters
when a platform runs migrations for multiple applications or customers.

The migration module does not choose its database credentials, authoritative
owner, project schema, approval, or audit actor.

## Names and ordering

Give every migration a stable, descriptive name:

```ts
export const name = "add_account_status";
```

The CLI discovers `.ts`, `.mts`, `.cts`, `.js`, `.mjs`, and `.cjs` files,
ignores `.d.ts` files, and processes filenames in lexicographic order. Timestamp
prefixes therefore produce a predictable sequence:

```text
20260715090000_create_accounts.ts
20260715103000_add_account_status.ts
20260716081500_add_account_status_index.ts
```

After a migration has been applied, do not rename it or change its contents.
Create a new forward migration instead.

## Validate, plan, preview, and apply

These commands answer different questions.

### Preview

Preview shows the structured operations produced by a migration module. It does
not connect to a database.

### Validate

JavaScript `validate()` checks that the migration is well formed, supported by
the selected dialect, and allowed by the supplied table ownership registry. It
does not inspect the live database.

### Plan

JavaScript `plan()` returns the same offline validation result together with the
migration document for review. It does not render SQL, detect live schema
differences, or classify every apply-time database condition.

### Apply

Apply adds the trusted host inputs, performs the target-specific safety checks,
acquires the project lock, checks migration history, executes pending work, and
records the result.

The public Node and CLI apply paths currently execute **DDL only**. They can
validate and preview `insert`, `update`, `delete`, and `backfill` operations, but
they do not execute those operations. A mixed migration can therefore apply its
schema changes while omitting its data changes. Use a Rust integration for data
migration execution, or split and run the data work through a separately
reviewed application job.

## Project identity and ownership

The main host inputs are:

- `ownerApp`: the trusted identity of the application deploying the migration;
- `projectSchema`: the SQL namespace owned by that application;
- `registry`: a map from existing table names to their trusted owners.

For example:

```ts
const registry = {
  accounts: "app_identity",
  orders: "app_orders",
};
```

A migration can create and then alter a table in the same module without a
registry entry. A later migration that alters the existing table needs a
matching entry. Missing or mismatched ownership fails closed.

`projectSchema` is a confinement boundary, not a provisioning request. Create
the schema or database before applying the migration.

## Policy and approval

Policy controls which capabilities a migration may use, including destructive
changes, raw SQL, cross-schema access, roles, extensions, and optional required
table shape.

The public Node API uses the built-in confined policy and does not expose custom
policy composition. Platforms that need custom policy can make those decisions
in a Rust host, but arbitrary policy configuration is not available to the
public apply API yet.

Destructive work requires explicit operator approval. The Node API exposes an
`approved` boolean; the CLI does not expose approval. Approval should always be
bound to the exact migration content that was reviewed.

See [Policy model](policy.md) and [Security model](security-model.md).

## The migration journal

Every completed migration adds an event to an append-only journal. The journal
captures migration identity, checksum, actor, and time so zero-migrate can:

- detect changed content for an already-known migration;
- show PostgreSQL history;
- prevent unsafe reapplication;
- recover supported non-transactional work after interruption.

JavaScript `status()` currently reads journal state with an empty migration set,
so it does not discover pending files in a directory. JavaScript `history()` is
currently PostgreSQL-only.

## Transactions and partial completion

A directory of migration files is not one global transaction. If an earlier
migration succeeds and a later one fails, the earlier migration remains
applied.

PostgreSQL and SQLite can commit supported transactional schema work together
with its journal event. MySQL DDL auto-commits, so interrupted work uses recovery
state and requires extra operational care.

## Drift and rollback

Apply detects changed migration content through journal checks. Structural drift
between the expected and live schema is a separate, explicit Rust workflow; it
is not checked automatically by JavaScript apply.

There is no public high-level rollback command. Prefer a reviewed forward-fix
migration. For irreversible data loss, use a tested backup and restore process.
