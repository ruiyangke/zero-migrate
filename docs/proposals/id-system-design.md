# ID system design proposal

Status: Draft
Date: 2026-07-16

This proposal defines how zero-migrate should represent primary keys and other
identifiers across PostgreSQL, MySQL 8, SQLite, and JavaScript.

The central design rule is simple:

> An ID is a role, not a database type.

An ID system combines storage, generation, constraints, ownership, and
presentation. The migration API should express only the database-relevant
choices and leave application ownership and presentation outside the tool.

## Proposed decisions

1. Keep physical storage in the existing `t.*` type system.
2. Keep primary keys, unique constraints, and foreign keys separate from value
   generation.
3. Remove `t.id()`. Require storage, generation, and the key constraint to be
   visible in migration source.
4. Add an `ids` namespace only for stored value formats that add enforceable
   schema validation or comparison semantics, initially TypeID and ULID.
5. Treat UUID versions as generator semantics. UUIDv4 and UUIDv7 use the same
   logical UUID column type.
6. Derive database generation from executable defaults and identity facets.
   Treat application, client, service, external, and caller assignment as
   supplied values. Do not encode the external generator in migration IR.
7. Keep application runtime generators, codecs, JSON conventions, and nominal
   TypeScript types outside zero-migrate.
8. Make every reference artifact self-contained with an explicit local type or a
   type resolved from the declared schema graph before canonical IR is recorded.
   A live catalog may validate the type, but never choose it. Format checks live
   on keys; a reference inherits format-safety through referential integrity and
   carries no check of its own, which also makes typed foreign keys portable on
   MySQL.
9. Model composite identity as an ordered table-level tuple. Keep composite
   foreign keys as named table-level constraints, and support both across all
   three targets without an `ids.composite()` value helper.
10. Preserve large integer migration values with `int64(bigintOrString)` and
    decimal-string IR. Do not coerce them through JavaScript `number`.
11. Model changing an existing table's ID as a staged expand, backfill, verify,
    constrain, and cutover workflow.

## Recommended defaults

There is no universal best ID for every application:

| Situation | Recommended starting point |
| --- | --- |
| One authoritative relational database | Signed `BIGINT` identity |
| Distributed or offline writers | Externally supplied UUID, commonly UUIDv7 |
| Random ID with no embedded time | UUIDv4 |
| Human-visible typed public ID | Externally generated TypeID |
| Join table | Composite primary key when the tuple is the identity |
| External integration | Internal surrogate key plus scoped external unique key |
| Stable compact domain code | Natural key or alternate unique key |
| Distributed compact integer requirement | Snowflake-family ID generated by a service |

There is no universal ID shorthand. A database-generated UUIDv4 primary key is
written explicitly:

```ts
id: t.uuid()
  .notNull()
  .primaryKey()
  .default(uuidV4())
```

The generated value must be a canonical RFC 9562 UUIDv4 on every target,
database version, storage engine, and replication configuration that passes the
capability check. Unsupported combinations fail before DDL execution. The
current PostgreSQL UUIDv4, MySQL UUIDv1, and SQLite non-RFC hex divergence is not
part of the new contract.

Database-generated UUID defaults have target and replication limitations. The
portable distributed migration shape is an externally supplied UUID column:

```ts
// Migration schema: supplied by the application, so there is no SQL default.
id: t.uuid().primaryKey()
```

An application may choose UUIDv7, but zero-migrate neither generates nor proves
the version of externally supplied UUIDs unless the schema includes an explicit
user-authored version check.

## What established tools teach us

Existing schema tools converge on two useful patterns:

| Tool | ID shape | Lesson for zero-migrate |
| --- | --- | --- |
| Rails | `create_table` adds an auto-incrementing `id` primary key by default; UUID is an explicit table option | A one-line conventional default is valuable when its expansion is stable |
| Prisma | Scalar type, `@id`, and `@default(...)` are separate; defaults include auto-increment, UUIDv4, UUIDv7, ULID, and application-level string generators | Type, key role, and generation should remain independently expressible |
| Django | An omitted key becomes `BigAutoField`; UUID examples declare `UUIDField(primary_key=True, default=uuid.uuid4)` | Implicit integer IDs and explicit application-generated UUIDs are both familiar |
| Drizzle | Column type, `.primaryKey()`, database identity, server defaults, runtime defaults, and TypeScript brands are separate operations | Database generation and application runtime generation must not share one vague default |
| SQLAlchemy | `primary_key`, `Identity`, `Sequence`, client defaults, and server defaults are separate concepts | Assignment authority is part of the contract, not merely renderer syntax |
| Knex | `increments()` is a bundled convenience, while UUID type, primary key, and default are composable | Convenience recipes are useful, but target-specific UUID helpers can silently produce different UUID versions |

The established pattern is composition. zero-migrate adopts that pattern without
adding a universal ID shortcut or a parallel ID type system. Physical type, key
constraint, and executable generation remain the source of truth. Format
metadata exists only where it enables enforceable storage validation or
comparison behavior.

## Goals

- Make the common primary-key cases easy to discover and author.
- Give every public helper one stable meaning across deployment profiles.
- Support database-generated and externally generated values honestly.
- Preserve consistent JavaScript migration literals and canonical IR across
  targets.
- Support primary IDs, public IDs, external IDs, natural IDs, and composite IDs.
- Make references declare or deterministically inherit the referenced key's
  physical type and stored format when schema metadata exists.
- Validate impossible or unsafe combinations before DDL execution.
- Support imports and backfills without pretending generated IDs are gapless.
- Keep community ID formats usable without adding a database type for every
  library-defined algorithm.

## Non-goals

- IDs are not authorization tokens or access-control checks.
- Generated integers are not gapless business sequence numbers.
- ID ordering is not transaction commit order.
- An ID timestamp is not a replacement for `created_at`.
- zero-migrate will not add dedicated physical database types for every ID
  library.
- The first implementation will not automatically replace an existing table's
  primary key in one operation.
- A migration declaration cannot make an arbitrary third-party database client
  generate application-owned IDs automatically.

## Portability limitations

One migration source stays portable across PostgreSQL, MySQL 8, and SQLite, but a
few properties remain target-shaped. They are stated here rather than buried:

- There is no portable one-statement primary-key add on a populated table. Adding
  or changing a key is always the staged workflow below.
- Generated integers are database-allocated and may have gaps. No ID family
  promises gaplessness or non-reuse.
- A resumable backfill's bounded cohort does not cover rows inserted after cohort
  capture; the migration must establish a write invariant or a final catch-up.
- Compact 16-byte binary UUID storage is deferred; the portable UUID storage is
  canonical text with a syntax check.
- Native database UUID generators are version-gated (PostgreSQL 13+ for v4,
  PostgreSQL 18+ for v7; MySQL and SQLite synthesize v4 and never generate v7).
  The portable distributed shape is an externally supplied UUID.

## The ID model

Every ID design has five independent axes.

### 1. Role

- Surrogate row ID
- Natural or domain ID
- Composite ID
- Public ID
- External ID
- Deterministic or content-derived ID

### 2. Storage

- `smallInt`, `int`, or `bigInt`
- Logical UUID
- Text or fixed-length character data
- Binary data
- A tuple of multiple columns

### 3. Assignment authority

- Database identity or sequence
- Database default function
- Application or server
- Client or browser
- Dedicated ID service
- External provider
- Caller-supplied value
- Deterministic derivation

These distinctions matter to the wider system, but zero-migrate records only
what it can enforce: database identity, a database expression, or a supplied
value. Every non-database authority is simply "supplied" in migration IR.
Apply-engine generation is a separate migration-only operation used for
backfills; it says nothing about future application writes.

### 4. Constraint

- Primary key
- Unique key
- Composite primary or unique key
- Foreign key
- No key constraint

### 5. Stored representation

- Raw integer or UUID
- Canonical string encoding
- Stored prefix such as `user_...`

The product design must not collapse these axes into one ambiguous `id` flag.
Migration IR records only the axes that affect schema, execution, or validation.
Application presentation and organizational ownership stay outside it.

## Survey of commonly used ID families

| Family | Typical storage | Usual assignment | Ordering | zero-migrate support |
| --- | --- | --- | --- | --- |
| Integer auto-increment or identity | Signed integer | Database | Allocation order | Existing first-class facets |
| Sequence-backed integer | Signed integer | Database sequence | Sequence order | First-class, PostgreSQL sequence API |
| UUIDv4 | UUID or canonical text | Database or application | Random | UUID storage plus exact generator |
| UUIDv7 | UUID or canonical text | Usually application | Approximate creation time | UUID storage plus exact generator |
| UUIDv1 | UUID | Database or application | Time-derived but not canonically sortable | Generic UUID, not recommended |
| UUIDv6 | UUID | Database or application | Time ordered and reordered for sorting | Generic UUID |
| UUIDv3 or UUIDv5 | UUID | Deterministic application function | Deterministic | Generic UUID |
| UUIDv8 | UUID | Custom application algorithm | Custom | Generic UUID |
| ULID | 26-character text or 16 bytes | Application | Millisecond ordered | First-class logical recipe |
| TypeID | Prefix plus 26-character UUIDv7 suffix | Application | Millisecond ordered by suffix | First-class logical recipe |
| KSUID | 27-character text or 20 bytes | Application | Second ordered | Generic assigned text or bytes |
| XID | 20-character text or 12 bytes | Application | Second ordered | Generic assigned text or bytes |
| TSID | 64-bit integer or 13-character text | Application | Millisecond ordered | Generic assigned integer or text |
| COMB or sequential GUID | UUID-compatible bytes | Database or application | Algorithm-dependent | Generic UUID storage |
| Snowflake family | Positive signed `BIGINT` | Application or ID service | Layout-dependent | Generic assigned `bigInt` |
| MongoDB ObjectId | 12 bytes or 24 hex characters | MongoDB driver | Roughly second ordered | Generic interop storage |
| NanoID | Usually 21 text characters | Application | Random | Generic assigned text |
| CUID2 | Usually 24 text characters | Application | Random-looking | Generic assigned text |
| Natural ID | Domain-specific | Caller or upstream | Domain-specific | Existing primitives plus constraints |
| Composite ID | Multiple columns | Any authority | Tuple-dependent | Existing table-level constraints |
| External ID | Usually text | External provider | Provider-dependent | Existing primitives plus scoped unique constraint |
| Content hash | Binary or fixed hex | Deterministic application function | Hash order | Existing bytes or character primitives |

RFC 9562 specifies layouts for UUIDv1 and UUIDv3 through UUIDv8, and reserves
UUIDv2 for DCE Security. These versions are generation formats, not separate
database column types. RFC 9562 recommends UUIDv7 over UUIDv6 for new
time-ordered systems without a UUIDv1 compatibility requirement.

XID, TSID, COMB, Sonyflake, and similar names represent useful algorithm
families, but they do not each require a dedicated database type. A generic
assigned integer, text, UUID, or binary column is the long tail of the design.

## Public JavaScript API

### Layer 1: the common case is explicit

```ts
table("users").create({
  columns: {
    id: t.uuid().primaryKey().default(uuidV4()),
    email: t.text().notNull(),
  },
});
```

The declaration exposes every consequential choice:

- logical UUID storage;
- ordinary column-level primary-key constraint;
- database default that generates an exact UUIDv4;
- no stored prefix.

The primary-key constraint implies non-nullability. There is no hidden ID marker
and no policy may reinterpret this declaration as text, an externally supplied
value, or a different UUID version.

### Layer 2: other primitive compositions

Users express storage, executable generation, and key constraints separately:

```ts
table("examples").create({
  columns: {
    // Portable database-generated integer.
    integer_id: t.bigInt().primaryKey().autoIncrement(),

    // Database SQL generates an exact UUIDv4.
    random_id: t.uuid().default(uuidV4()).unique(),

    // An external writer supplies a UUID. No SQL default is recorded.
    ordered_id: t.uuid().unique(),

    // The application or a dedicated service supplies this positive bigint.
    snowflake_id: t.bigInt().unique(),

    // Generic assigned and imported formats use ordinary storage builders.
    nano_id: t.char({ length: 21 }).unique(),
    imported_object_id: t.char({ length: 24 }).unique(),
  },
});
```

The absence of a database default or identity means the value must be supplied
on insert. Whether the supplier is an application server, browser, ID service,
external provider, deterministic function, or human caller is outside the
migration schema because it does not change database DDL.

### Layer 3: validated value-format helpers

Only formats with a stable public specification and useful cross-database
validation receive dedicated column helpers:

```ts
import { ids, table, t } from "zero-migrate";

table("public_examples").create({
  columns: {
    typed_id: ids.typeId({ prefix: "example" }).notNull().unique(),
    event_id: ids.ulid().notNull().unique(),
  },
});
```

Proposed TypeScript surface:


`ids`, `uuidV4`, `uuidV7`, `perRow`, and `int64` are migration-package
exports. zero-migrate exposes no application-runtime ID package.

`perRow.*` values are valid only in `backfill({ set })`. They are not column
definitions, database defaults, ordinary insert or update values, or application
generators. The name describes their migration behavior: evaluate once for each
affected row.

Like ordinary `t.*` builders, `ids.typeId({ prefix })` and `ids.ulid()` are
nullable by default. They choose storage, canonical comparison behavior, and
value-format validation only. They do not imply a database generator,
`NOT NULL`, uniqueness, or a primary key. This makes the same helper usable
while adding a nullable candidate ID to an existing populated table. They make
no claim about which application library creates values or how application code
represents them.

The helper contract includes canonical database checks for prefix, length,
alphabet, and overflow bounds on authoritative columns (keys, candidate unique
columns, and standalone typed columns). A `.references()` column emits no check
of its own and inherits format-safety from the referenced key (see "Format
checks live on keys, not references"). PostgreSQL and SQLite can express those
checks; MySQL requires a version that enforces `CHECK` constraints. If a target
cannot enforce the promised format, validation fails rather than quietly
downgrading to application-only checking. Raw string literals in migration DML must already use
the canonical stored form. The recorder never infers a destination format and
rewrites an untyped string. When the declared project graph provides format
metadata, deterministic preflight validates the literal early; otherwise the
database constraint remains authoritative at apply. Application writers must
independently satisfy the same constraint.

KSUID, XID, TSID, NanoID, CUID2, Snowflake-family values, ObjectId, hashes,
proprietary IDs, and imported legacy formats remain expressible through integer,
UUID, text, or binary primitives plus constraints.

### Defining your own shortcuts

zero-migrate ships no universal ID shortcut, but column builders are ordinary
reusable values, so a project defines its own conventions in a few lines and
keeps them visible and greppable:

```ts
// project ids.ts
import { ids, t, uuidV4 } from "zero-migrate";

export const rowId = () => t.bigInt().primaryKey().autoIncrement();
export const uuidPk = () => t.uuid().primaryKey().default(uuidV4());
export const publicId = (prefix: string) =>
  ids.typeId({ prefix }).notNull().unique();
```

```ts
import { publicId, rowId } from "./ids";

table("orders").create({
  columns: {
    id: rowId(),
    public_id: publicId("order"),
  },
});
```

A helper that returns a whole key fragment (columns plus a composite `primaryKey`
array) lets a team standardize a tenant-scoped composite key without a built-in
`ids.composite()`. Because the expansion is authored in the project, its meaning
stays explicit, and no policy or engine version can reinterpret it.

### UUID value constructors

Replace the ambiguous `genRandomUuid()` vocabulary with explicit UUID
constructors:

```ts
uuidV4()
uuidV7()
```

These are database SQL expression constructors. They can appear in a column
default or in a data-migration expression, and the database evaluates them. They
are never evaluated by JavaScript while recording a migration and never switch
silently to apply-engine generation.

```ts
id: t.uuid().notNull().default(uuidV4())
```

Rules:

- `uuidV4()` must always create RFC 9562 UUIDv4.
- `uuidV7()` must always create RFC 9562 UUIDv7.
- A target that cannot provide the exact requested database generator fails
  validation or apply with a version/capability error.
- The renderer must never substitute UUIDv1 for UUIDv4 or UUIDv7.
- `genRandomUuid()` becomes a deprecated source-level alias for `uuidV4()` and
  records the same exact UUIDv4 expression.

The UUID version describes the generated value, not the storage type. A UUID
column can still accept a caller-supplied UUID of another version unless the
application or a target-specific check validates it.

### Database-generated versus supplied values

The distinction is observable and must be documented:

```ts
// Any database writer may omit the column.
t.uuid().default(uuidV4())

// The database has no default. The application supplies the value.
t.uuid()
```

Database generation means a SQL default or identity exists. Explicit values may
still override an ordinary default. PostgreSQL `IDENTITY ALWAYS` is the exception
and is target-specific.

An application, client, service, external provider, or caller-supplied value has
no database default. Raw SQL, a generic driver, or an ORM must supply it. This is
not called "application-generated" in migration IR because the database cannot
prove which external actor created it.

zero-migrate does not provide a runtime generator, ORM hook, driver codec, or
application JSON contract. Applications choose their own libraries and are
responsible for producing values accepted by the recorded database schema.
Random or time-based values used during migration apply must use a database SQL
expression or the apply-engine `perRow.*` vocabulary.

### Auto-increment and identity integers

The existing compositional API remains canonical:

```ts
// Portable intent.
id: t.bigInt().primaryKey().autoIncrement()

// PostgreSQL-specific "always" behavior, capability-gated elsewhere.
id: t.bigInt().primaryKey().identity({ always: true })
```

The portable `autoIncrement()` contract is database-owned allocation, explicit
import support, allowed gaps, and no promise that allocation order equals commit
order. It does not promise gaplessness or universal non-reuse.

SQLite can auto-generate this value only on a rowid table when the column is the
table's sole single-column primary key and lowers to
`INTEGER PRIMARY KEY AUTOINCREMENT` under the existing portable facet. A
secondary generated integer column and a `WITHOUT ROWID` table are rejected for
SQLite. `AUTOINCREMENT` prevents reuse of previously committed rowids but has
extra cost; a future SQLite-specific bare-rowid option must use a different,
explicit contract rather than silently changing `autoIncrement()`.

MySQL permits only one `AUTO_INCREMENT` column per table and requires it to be
indexed. PostgreSQL supports more identity shapes, including `always`, but those
are not portable. The validators enforce these differences.

`smallInt` remains available through primitives but is not recommended as a
general-purpose generated ID because its range is small.

### TypeID and typed IDs

`ids.typeId({ prefix })` means the published TypeID format, not any arbitrary
prefixed ID:

```text
<prefix>_<26 lowercase Crockford Base32 characters>  // nonempty prefix
<26 lowercase Crockford Base32 characters>           // empty prefix
```

The suffix encodes UUID bytes. The full value is stored as text. The prefix is
part of the persisted value and public compatibility contract.

```ts
id: ids.typeId({ prefix: "user" }).primaryKey()
```

Validation follows TypeID 0.3:

- prefix is at most 63 characters;
- prefix contains lowercase ASCII letters and underscores;
- a nonempty prefix starts and ends with a letter;
- an empty prefix omits the underscore entirely;
- the complete value is at most 90 characters;
- the suffix is exactly 26 lowercase Crockford Base32 characters;
- the first suffix character satisfies the TypeID 128-bit overflow bound;
- parsers accept UUID versions and variants permitted by the TypeID
  specification;
- `perRow.typeId({ prefix })` creates a UUIDv7-backed TypeID only for
  migration backfills.

This follows the full format rather than making every stored value pass a
stricter UUIDv7-only rule. Generation and parsing are separate contracts.
For externally supplied values, the schema does not prove which library created
the suffix, the quality of its randomness, or the application's clock behavior.

The existing internal `<prefix>_<22 base62 UUIDv7>` format is not TypeID. It may
remain the internal wire format for migration IDs and old platform data, but new
user-facing documentation must not call it TypeID.

### Stored prefixes are schema semantics

```ts
// Stored value: user_01h...
id: ids.typeId({ prefix: "user" }).primaryKey()
```

The prefix affects stored values, validation, comparison, and references, so it
belongs in migration schema. Application-level nominal types such as `UserId`
do not affect the database and remain entirely in application code.

### ULID

```ts
id: ids.ulid().primaryKey()
```

ULID input is case-insensitive by specification, but the schema contract stores
canonical 26-character uppercase Crockford Base32. Raw migration literals must
already be uppercase, while `perRow.ulid()` emits the canonical form during
backfills. The database check rejects lowercase or invalid values from every
other writer. Canonical storage uses binary/ASCII ordering when lexical time
ordering is expected. The application independently chooses its ULID library and
whether it needs process-local monotonic generation.

The database constraint proves representation, not provenance. It cannot prove
generator entropy, clock correctness, monotonicity, or global ordering. A
primary-key or unique constraint remains responsible for collision enforcement.

UUIDv7 remains the preferred general distributed ID because it uses standard
UUID storage and tooling. ULID is appropriate when its 26-character textual form
is itself a product requirement.

An empty-prefix TypeID and a ULID are both 26 Crockford Base32 characters and are
distinguished only by canonical case: a TypeID suffix is lowercase, a ULID is
uppercase. The case rules keep a typed column unambiguous, but a mis-cased raw
literal passes one format check and fails the other, so author every literal in
the exact canonical case of its declared column.

### Snowflake-family IDs

```ts
id: t.bigInt().primaryKey()
```

Snowflake is a family, not one interoperable format. The storage contract is an
application-supplied positive signed `BIGINT`; an optional check can enforce
positivity. zero-migrate does not define an epoch, bit layout, or worker
allocator. The application or ID service owns worker identity, clock rollback
handling, and sequence allocation.

Migration DML uses the tagged `int64` value defined below. Application runtime
and JSON representations are outside zero-migrate.

### Natural IDs

A natural key uses its real domain type:

```ts
table("countries").create({
  columns: {
    code: t.char({ length: 2 }).notNull(),
    name: t.text().notNull(),
  },
  primaryKey: ["code"],
});
```

Use a natural primary key only when it is immutable, canonical, compact,
non-sensitive, and controlled for the row's full lifetime. Email addresses,
phone numbers, mutable usernames, and editable slugs usually belong under a
unique constraint beside a surrogate key.

### Composite IDs

Composite identity is an ordered tuple and remains table-level:

```ts
table("orders").create({
  columns: {
    tenant_id: t.uuid().notNull(),
    order_id: t.uuid().notNull(),
    status: t.text().notNull(),
  },
  primaryKey: ["tenant_id", "order_id"],
});

table("order_lines").create({
  columns: {
    tenant_id: t.uuid().notNull(),
    order_id: t.uuid().notNull(),
    line_no: t.int().notNull(),
    description: t.text().notNull(),
  },
  primaryKey: ["tenant_id", "order_id", "line_no"],
  foreignKeys: [
    {
      name: "order_lines_order_fk",
      columns: ["tenant_id", "order_id"],
      references: {
        table: "orders",
        columns: ["tenant_id", "order_id"],
      },
    },
  ],
});
```

The array order is part of the contract. It determines tuple correspondence,
index prefix behavior, canonical IR, and constraint lowering order. At table
creation, composite keys are authored only with the table-level `primaryKey`
array. Repeating `.primaryKey()` on multiple columns is rejected rather than
implicitly creating an ordered tuple. Existing tables use the explicit
`.primaryKey().add()` or `.primaryKey().replace()` operations described below.

Every component retains its own storage, value format, and generation authority.
In the example, an external writer supplies both UUID components and the line
number because none has a database default. There is no `ids.composite()` because
a composite key is not one stored scalar or one standardized value format.

Portable schemas do not use `autoIncrement()` inside a composite primary key.
SQLite automatic generation requires the exact single-column `INTEGER PRIMARY
KEY` shape, and the supported MySQL contract also requires an auto-incrementing
column to be the single-column primary key. A PostgreSQL-only identity component
is target-gated and still leaves the remaining components separately supplied.

Use a surrogate primary key plus a composite unique index when the natural tuple
is wide, mutable, sensitive, or propagated through many child tables. Use the
composite tuple as the primary key when the tuple itself is stable domain
identity, as with many join tables and tenant-scoped keys.

### External IDs

External values are usually unique only inside a provider, account, or tenant:

```ts
table("connections").create({
  columns: {
    id: t.bigInt().primaryKey().autoIncrement(),
    provider: t.text().notNull(),
    external_id: t.text().notNull(),
  },
  indexes: [
    {
      name: "connections_provider_external_uq",
      on: ["provider", "external_id"],
      unique: true,
    },
  ],
});
```

External IDs should follow the provider's documented canonicalization and
comparison rules. Do not coerce digit-shaped values to numbers because leading
zeros and future provider formats may be meaningful.

### Public and internal IDs

A table may deliberately have both:

```ts
table("orders").create({
  columns: {
    id: t.bigInt().primaryKey().autoIncrement(),
    public_id: ids.typeId({ prefix: "order" }).notNull().unique(),
  },
});
```

This is useful when a compact internal key and a stable public API key solve
different requirements. Clustering benefits are engine-specific, especially on
InnoDB, so they are not part of the cross-database contract. A second public ID
should not be added automatically to every table.

## References and foreign keys

The current `t.ref("accounts")` always records text, so it cannot safely represent
integer, UUID, TypeID, or binary keys. Replace it with an explicitly typed local
column and reference facet:

```ts
account_id: t.uuid().references("accounts", "id")
```

This artifact is self-contained: `account_id` is UUID even when the target table
is not available during offline recording. The reference adds:

- target table and column identity;
- foreign-key behavior;
- compatibility validation against the target key.

It does not add a generator, default, primary key, or unique constraint. A text
format helper preserves its own length, canonicalization, and collation:

```ts
account_id: ids.typeId({ prefix: "account" })
  .notNull()
  .references("accounts", "id")
```

Reference compatibility includes the lowered storage type, exact
`ValueFormat`, TypeID prefix, and collation. For example, an `account_...`
column cannot reference a target declared with prefix `acct`, even though both
are physically text.

### Format checks live on keys, not references

A format-typed column emits its database format check only when it is an
authoritative value: a key, a candidate unique column, or a standalone typed
column. A `.references()` column emits no format check of its own. Referential
integrity already guarantees that every non-null value exists in the referenced
key, and that key enforced the format on insert, so a duplicate check on the
child is redundant. The format guarantee flows down the reference chain, and the
authoritative check lives at its root.

This is also what makes format-typed foreign keys portable on MySQL. MySQL
forbids a column from carrying both a `CHECK` and foreign-key referential
actions. Because reference columns now carry no format check, `onDelete` and
`onUpdate` are allowed on typed references on every target, and the same
migration renders the same shape everywhere rather than silently dropping the
action on MySQL. `SET NULL` writes null; `SET DEFAULT` must still satisfy the
foreign key. A column that is both a primary key and a reference (1:1
inheritance) inherits its format guarantee from the referenced parent.

The only column that would otherwise carry both a check and referential actions
is a format-typed reference to an unchecked target, and that combination is
already rejected by reference compatibility, so the conflict is structurally
impossible instead of a documented hazard.

When the target is in the declared project artifact graph, its stored format is
a deterministic recording input and must match the local format. Deployed
catalog or journal state may validate recorded metadata but never supply it. If
an unmanaged target has no format metadata, a format-bearing reference cannot be
proven safe and is rejected until that metadata is imported into the project
graph. A plain primitive reference can still be validated physically from the
catalog.

A future schema-handle API may infer the local type only when it can resolve the
target from the declared schema graph before canonical IR is finalized. That
inference surface is intentionally deferred rather than adding an undefined
handle model to this proposal.

The live catalog may validate a recorded local type, but it never selects that
type. Otherwise the same migration could record different artifacts in different
environments. Remove `t.ref()` from the pre-release public API after migrating
the repository's own examples and fixtures to `.references()`.

Composite foreign keys use the table-level `foreignKeys` API with explicit
ordered local and referenced column lists. Repeating column-level `.references()`
creates independent foreign keys and must never be interpreted as one composite
relationship.

For a composite foreign key, validation requires:

- equal, nonzero local and referenced arity;
- no duplicate or missing columns;
- exact positional correspondence in the declared order;
- compatible logical storage and integer width for each position;
- matching value format, TypeID prefix, ULID rules, and collation;
- a referenced tuple backed by a primary-key or unique candidate-key contract.

PostgreSQL, MySQL, and SQLite all support composite foreign keys. The current
engine's PostgreSQL-only lowering is an implementation gap, not part of the
public design. MySQL and SQLite lowering and introspection must be completed
before zero-migrate claims cross-database composite-reference support.

The portable null contract is SQL `MATCH SIMPLE`: if any local component is
null, the row does not need a matching parent. Required relationships declare
every local component `NOT NULL`. An optional all-or-none tuple needs an explicit
portable check; the API does not promise `MATCH FULL`, which SQLite does not
enforce. Foreign-key creation also verifies or plans supporting indexes in the
required column order and shows every created index in the migration preview.

Create-time composite foreign keys lower directly on every target. Adding,
dropping, or changing one on SQLite requires a table rebuild that preserves the
remaining schema objects. The rebuild replaces the table and recreates its
schema objects inside a transaction, then runs `foreign_key_check` before
commit. The transaction makes the result externally atomic.

## Physical storage policy

### UUID

Use this migration-friendly logical UUID mapping:

| Target | Default physical storage | Migration DML representation |
| --- | --- | --- |
| PostgreSQL | Native `uuid` | Canonical string |
| MySQL 8 | Canonical 36-character text with bytewise comparison | Canonical string |
| SQLite | Canonical 36-character `TEXT` | Canonical string |

The MySQL and SQLite mappings include a database check for exact lowercase
8-4-4-4-12 hexadecimal syntax. This prevents case variants or arbitrary
36-character strings from becoming distinct representations of the same logical
UUID. A target that cannot enforce this logical-type contract fails the
capability check.

SQLite checks must test the stored value's type as well as its spelling. Every
nullable logical UUID, TypeID, or ULID check has this shape:

```sql
CHECK (
  column_name IS NULL OR
  (typeof(column_name) = 'text' AND <format predicate>)
)
```

The format predicate contains the exact length, alphabet, case, separator, and
overflow rules for that logical format. `NOT NULL` remains a separate column
constraint. Text affinity alone is not a format guarantee, and a BLOB must not
pass merely because its bytes have the expected length. This contract does not
require callers to create SQLite `STRICT` tables.

Compact 16-byte MySQL and SQLite storage can be added later as an explicit
storage policy, but it requires an exact migration wire representation and
binary-cursor support. Application driver integration remains the application's
responsibility.

UUID literals authored in migration DML must already use canonical lowercase
8-4-4-4-12 form. zero-migrate does not rewrite untyped strings. Values written by
applications must independently satisfy the database constraint.

### Textual IDs

Text comparison is format-specific:

- TypeID is strictly lowercase and uses bytewise comparison.
- ULID accepts case-insensitive input but is stored as canonical uppercase; its
  canonical values use bytewise comparison for lexical time order.
- NanoID comparison follows the configured alphabet and cannot be guessed by a
  generic text helper.
- External IDs follow provider-defined normalization and comparison rules.
- UUID migration literals must already use canonical lowercase.

Default MySQL collations are often case-insensitive, so canonical TypeID and
ULID helpers select an ASCII/binary-compatible collation. PostgreSQL and SQLite
must also preserve canonical lexical ordering when ordering is part of the
format contract.

### Integers

Portable integer IDs are signed. MySQL unsigned integers have no equivalent
range in PostgreSQL or SQLite and remain a MySQL-specific choice.

## Migration JavaScript and wire values

This contract applies only to values authored in JavaScript migrations and their
canonical IR. It makes no promise about application objects, JSON APIs, ORMs, or
raw database drivers.

| Storage family | JavaScript migration value | Migration IR wire |
| --- | --- | --- |
| `smallInt` and `int` | Safe `number` | JSON number |
| `bigInt` and Snowflake-family | `int64(bigintOrString)` | `{"int64":"..."}` |
| UUID | Canonical string | JSON string |
| ULID, TypeID, NanoID, CUID2, KSUID | String satisfying the schema format | JSON string |
| Binary/hash | `Uint8Array` | `{"bytes":"<base64>"}` |
| Composite key | No scalar form; operations name each column | Ordinary per-column wire values |

The `primaryKey` array, foreign-key column arrays, and DML field names carry
composite identity. JavaScript object enumeration is never used to infer key
order, and migration IR has no composite scalar.

The migration value vocabulary needs an exact signed 64-bit constructor because
JavaScript `number` cannot represent every database `BIGINT`:

```ts
int64(9_223_372_036_854_775_000n)
int64("9223372036854775000")
```

The recorder converts `int64(...)` to the tagged decimal-string wire value. Raw
JavaScript `bigint` is not accepted as a generic migration scalar because native
JSON serialization cannot represent it.

## Dialect capability matrix

| Capability | PostgreSQL | MySQL 8 | SQLite |
| --- | --- | --- | --- |
| Signed integer identity | Native | `AUTO_INCREMENT` | `INTEGER PRIMARY KEY` |
| Identity `always` mode | Yes | No exact equivalent | No exact equivalent |
| Native UUID storage | Yes | No | No |
| Native database UUIDv4 generator | PostgreSQL 13+ | No | No |
| Exact synthesized database UUIDv4 default | Not needed on PostgreSQL 13+ | Capability-gated | Create-table path only |
| Native database UUIDv7 generator | PostgreSQL 18+ | No | No |
| Externally supplied UUIDv4 or UUIDv7 | Yes | Yes | Yes |
| TypeID or ULID storage | Text | Text | Text |
| Native TypeID or ULID generator | No | No | No |
| Composite primary key | Yes | Yes | Yes |
| Create-time composite foreign key | Yes | Yes | Yes |
| Add or change composite foreign key without rebuild | Yes | Not guaranteed | No |
| Referential action on a typed reference column | Yes | Yes | Yes |
| Add primary key without table-specific work | No universal online guarantee | Rebuilds clustered organization | Requires rebuild |

Important target rules:

- PostgreSQL identity requires PostgreSQL 10 or newer.
- PostgreSQL core `gen_random_uuid()` requires PostgreSQL 13 or newer. Older
  versions require an extension.
- PostgreSQL core `uuidv7()` requires PostgreSQL 18 or newer.
- MySQL expression defaults require InnoDB on MySQL 8.0.13 or newer for this
  contract. Exact UUIDv4 uses a random-byte expression that sets RFC version and
  variant bits and emits canonical 36-character text. It never uses `UUID()`.
- The complete MySQL logical UUID contract requires 8.0.16 or newer so the
  canonical syntax check is enforced. MySQL 8.0.13 through 8.0.15 can support an
  expression default but not the full logical type guarantee.
- TypeID and ULID database validation on MySQL requires 8.0.16 or newer, when
  `CHECK` constraints are enforced.
- MySQL foreign-key alteration may require a copying table rebuild while
  `foreign_key_checks` remains enabled. zero-migrate never disables enforcement
  implicitly to request an in-place algorithm; any optimized maintenance path
  must be explicit and prove its own validation and locking plan.
- MySQL prohibits foreign-key referential-action clauses on a column that also
  carries a `CHECK`. Because format checks live on keys and not on references
  (see "Format checks live on keys, not references"), a typed reference column
  carries no check, so `onDelete` and `onUpdate` are allowed on UUID-text,
  TypeID, and ULID references on MySQL exactly as on the other targets.
- Row-based MySQL replication is an ongoing deployment requirement for a
  nondeterministic UUID default when primary and replica must receive identical
  values. Apply validates current capability, but cannot guarantee that an
  operator will not change `binlog_format` later. Statement-based replication is
  rejected for that guarantee.
- SQLite has no native UUID function. A synthesized UUIDv4 expression must set
  both RFC version and variant bits and emit canonical 36-character text.
- SQLite foreign-key enforcement must be enabled on every connection. Apply
  verifies enforcement before relying on composite or single-column references.
- SQLite cannot add a primary-key or expression-default column through ordinary
  `ALTER TABLE ADD COLUMN`.
- PostgreSQL logical replication does not copy schema DDL or sequence state.
  Promotion procedures for identity-backed tables must synchronize both.
- SQLite has no native replication contract. Systems that replay SQL statements
  must not assume independently evaluated random defaults produce equal values.

## Validation rules

### General

- A primary-key column is non-null. SQLite rendering emits explicit `NOT NULL`
  for every primary-key component except an exact `INTEGER PRIMARY KEY`, because
  ordinary SQLite rowid tables have legacy null behavior for other primary-key
  declarations.
- Composite primary keys use the table-level ordered column list. Multiple
  conflicting primary-key declarations are rejected by the ordinary constraint
  validator.
- Repeated column-level `.primaryKey()` facets cannot implicitly create a
  composite primary key. Authors must provide the ordered table-level list.
- Composite foreign keys require equal arity and positionally compatible local
  and referenced columns. Separate column-level references remain separate
  constraints.
- An ID generator never implies uniqueness by itself.
- Identity, ordinary default, and computed/generated column expressions are
  mutually exclusive.
- When neither identity nor a default exists, inserts must supply the value.
- On SQLite, auto-increment or identity is valid only for the sole
  `INTEGER PRIMARY KEY` column.
- On MySQL, at most one auto-increment or identity column is allowed. The
  supported cross-database contract requires it to be the sole primary-key
  column and satisfy InnoDB's `AUTO_INCREMENT` indexing rules.

### Type compatibility

- Identity and `autoIncrement()` require integer storage. `smallInt` remains
  valid for compatibility but is not recommended for general-purpose IDs.
- Snowflake-family storage uses signed `bigInt`; a generic check may require a
  positive value.
- UUID generators require logical UUID storage.
- TypeID requires canonical lowercase text and bytewise comparison. ULID stores
  canonical uppercase text and uses bytewise comparison for lexical ordering.
- A stored TypeID prefix cannot be attached to an ordinary UUID column.
- TypeID or ULID `valueFormat` conflicts with `caseSensitive: false` or any
  collation facet that weakens bytewise comparison. Validation rejects the
  artifact instead of allowing the generic text facet to override the format
  helper's contract.
- `perRow.uuidV4()` and `perRow.uuidV7()` may target only a logical
  UUID column.
- `perRow.typeId({ prefix })` may target only a TypeID column whose stored
  prefix exactly equals `prefix`.
- `perRow.ulid()` may target only a ULID column.
- TypeID and ULID per-row generators are rejected for generic text columns. A
  physical text type alone does not declare the required stored format.
- Foreign-key logical type and integer width must match before lowering. The
  planner then verifies physical type and collation compatibility on each
  target; SQLite's shared `INTEGER` lowering must not make `int` and `bigInt`
  appear logically interchangeable.
- Foreign-key value format, TypeID prefix, and collation must also match.
- A typed reference column carries no format check, so it accepts `onDelete` and
  `onUpdate` on every target, including MySQL; the referenced key carries the
  check.

### UUID generation

- UUIDv4 output has version bits `0100` and RFC variant bits `10`.
- UUIDv7 output has version bits `0111`, RFC variant bits `10`, and the RFC 9562
  timestamp layout.
- A generator request is never silently downgraded or replaced by a different
  UUID version.
- A database-generated UUIDv7 request fails on unsupported server versions or
  targets.

### Text formats

- TypeID follows its published prefix, suffix, case, alphabet, and length rules.
- ULID uses exactly 26 canonical uppercase Crockford Base32 characters and its
  first character satisfies the 128-bit overflow bound.
- Text formats that rely on lexical ordering require a compatible collation.
- Generic string IDs require the user to choose a length large enough for the
  application's generator.
- SQLite logical UUID, TypeID, and ULID checks are null-tolerant and require
  `typeof(column) = 'text'` before evaluating the format predicate.

### JavaScript integers

- Migration `number` ID values must be safe integers.
- Migration `bigInt` and Snowflake-family literals use the tagged `int64()`
  value.

## Creating a new table

New tables can use any supported composition directly because the primary key
and optional default are created with the table:

```ts
table("events").create({
  columns: {
    id: t.uuid().primaryKey(),
    payload: t.json().notNull(),
  },
});
```

For database-generated values, inserts can omit the ID only when a real database
default or identity exists. Here an external writer supplies the UUID. If the
application chooses UUIDv7, its runtime library and validation remain outside
zero-migrate.

## Adding an ID to an existing table

There is no safe portable one-statement operation that adds and populates a new
primary key on a populated table. zero-migrate should model the intent as stages:

1. Add a nullable column with no primary key, unique constraint, or volatile
   database default.
2. Establish a write invariant for new rows. Use application dual-write,
   a target-safe temporary or final database generator, or a maintenance window.
3. Backfill rows with null IDs in bounded batches.
4. Run a final catch-up and prove there are no nulls or duplicates while writes
   are blocked or the invariant remains enforced.
5. Build and validate uniqueness using the safest target-specific plan.
6. Establish `NOT NULL` where the primary-key operation does not already do so.
7. Attach or switch the primary key using a target-specific operation.
8. Keep or install a future-row database default only when database generation
   is the deliberate final contract.
9. Cut references and application reads over separately.

```text
add nullable column (no key, no volatile default)
  -> establish write invariant (new rows carry the value)
  -> backfill null rows in bounded batches   <- resume after crash
  -> final catch-up + prove no nulls/duplicates
  -> build + validate uniqueness
  -> set NOT NULL
  -> attach primary key
  -> (optional) install future-row default
  -> cut references and reads over
```

For a new composite ID, the workflow operates on the entire ordered tuple. Add
all candidate columns, establish writes for every component, backfill missing
components, prove tuple-wide non-nullability and uniqueness, migrate dependent
foreign-key tuples, and then attach the primary key. The planner never cuts over
only part of a composite identity.

A resumable bounded backfill needs a stable cursor that is complete, non-null,
unique, and immutable for the operation. Replace the current `cursorColumn`
field with one canonical `cursorColumns` tuple. A single-column cursor is written
as `cursorColumns: ["id"]`; there is no second spelling or compatibility
normalization in this pre-release design. Repository source, IR fixtures, and
development progress tables migrate directly to the tuple field.

Before execution, the planner proves that the ordered cursor tuple is backed by
a primary or unique candidate key with compatible comparison semantics. It
rejects any backfill assignment to a cursor component. Uniqueness alone does not
make a cursor immutable, so every resumable backfill also declares
`cursorStability`.

`{ mode: "guardUpdates" }` installs a zero-migrate-owned database guard before
capturing the cohort. The guard rejects any update that changes a cursor
component, survives an interrupted apply, and remains until the backfill reaches
its durable completion checkpoint. Installation and cleanup are journaled
obligations. Apply rejects targets or existing-trigger interactions for which it
cannot prove the guard works. `{ mode: "externalInvariant", name }` records a
named application or maintenance invariant that forbids cursor updates for the
entire operation, including time between a crash and resume. It requires
explicit destructive approval and is shown prominently in preview and status.

If the table has no usable unique tuple or neither stability mode is acceptable,
the planner refuses resumable backfill and requires one of three explicit paths:
a one-shot update under a maintenance window, a target-specific rebuild or
temporary surrogate, or creation of a stable unique cursor in an earlier
migration. It never pages on an unstable row locator.

Paging is lexicographic in the declared order. At cohort initialization, the
engine records the greatest matching tuple as `endCursor`. Each batch selects
rows strictly after `lastCursor`, at or before `endCursor`, ordered by every
cursor component, and limited by the batch size. Targets may use native row
comparison only when it has the same semantics; otherwise the lowerer emits the
equivalent disjunction of prefix equality and next-component comparison.

`lastCursor` and `endCursor` are typed scalar arrays with exactly the same arity
as `cursorColumns`. They use the ordinary tagged scalar wire codec and are never
delimiter-joined strings. Progress stores the cursor-column array, typed cursor
arrays, plan checksum, row count, batch count, and completion state. A batch's
data writes and checkpoint advance commit atomically. Resume refuses changed
columns, arity, scalar types, collation semantics, checksum, or cohort bound.

Cursor stability does not by itself handle newly inserted rows. Before cohort
capture, the migration must establish a write invariant that makes new rows fail
the backfill filter, or it must schedule a final catch-up while writes are
stopped. The bounded cohort never silently claims that concurrent inserts were
covered.

PostgreSQL may build a unique index concurrently before attaching a constraint.
A volatile UUID default can rewrite an existing PostgreSQL table, unlike an
eligible constant default. MySQL reorganizes InnoDB clustered storage when
adding a primary key or `AUTO_INCREMENT`, and online or instant ALTER support
depends on the exact server version and operation. SQLite can add a unique index
without a rebuild, but adding a primary key requires a table rebuild. The public
workflow can be portable even when execution plans are target-specific.

## Backfilling generated IDs

Backfill must generate a distinct value per row. A single random literal must
never be recorded at migration build time and reused for every row.

```ts
table("orders").backfill({
  set: {
    public_id: perRow.uuidV7(),
  },
  cursorColumns: ["id"],
  cursorStability: {
    mode: "externalInvariant",
    name: "orders_id_is_immutable",
  },
  where: (c) => c("public_id").isNull(),
  batchSize: 1_000,
});
```

`perRow.uuidV7()` has one authority: the apply engine creates a distinct
value for each affected row. It is separate from database SQL `uuidV7()`. A
migration may instead use SQL `uuidV7()` when the target passes the exact
database-generator capability check. The two migration authorities never switch
implicitly, and neither defines application runtime behavior.

Before changing any row, the planner resolves each destination from the declared
project schema and validates the generator against it. UUID generators require a
logical UUID destination. A TypeID generator requires `ValueFormat::TypeId` and
an exact prefix match. A ULID generator requires `ValueFormat::Ulid`. Generic
text is never treated as TypeID or ULID by inference. A live catalog may confirm
physical storage and constraints, but it cannot invent missing format metadata.
If the declared schema cannot resolve the destination contract, apply fails
before the first batch.

Binary UUID storage also requires backfill cursor support before it can become a
default. The current SQLite backfill path supports integer and text cursors, not
blob cursors.

## Imports and explicit overrides

Ordinary defaults are used only when a value is omitted, so an explicit imported
UUID or string wins.

Portable integer identity uses by-default semantics so imports can preserve
values. After an import, synchronize the associated generator so its next value
cannot collide, respecting its increment and direction and never moving an
already-higher generator backward. This requires coordination with concurrent
writers. MySQL normally advances `AUTO_INCREMENT` after an explicitly inserted
higher value. Ordinary SQLite rowid generation has no separate sequence, while
SQLite `AUTOINCREMENT` uses `sqlite_sequence`. The import API should expose one
`synchronizeIdentity()` intent and plan it per target.

MySQL treats an explicitly inserted `0` as a request to generate a value unless
`NO_AUTO_VALUE_ON_ZERO` is enabled. An import that must preserve a legacy zero ID
therefore validates and pins that SQL mode or rejects the row; it never silently
substitutes a new ID.

```ts
table("orders").column("id").synchronizeIdentity({
  writesQuiesced: "orders_import_window",
});
```

`synchronizeIdentity` requires an explicit acknowledgment naming the window or
invariant under which no concurrent writer allocates a colliding value, mirroring
the destructive-approval and `cursorStability` patterns elsewhere. The engine
cannot prove writer quiescence, so it records the operator's named assertion and
shows it in preview and status.

No generated ID family promises gaplessness. A unique or primary-key constraint
remains mandatory even for statistically collision-resistant values.

## Changing an existing primary-key family

Changing `BIGINT` to UUID, UUID to TypeID, a single key to a composite key, a
composite key to a surrogate key, or the order of composite components affects
every foreign key and index. It is not a column type change.

The eventual workflow needs:

1. New candidate ID columns.
2. A write invariant for every new component.
3. Backfill and tuple-wide non-null and uniqueness verification.
4. `NOT NULL` on every candidate primary-key component.
5. A unique candidate-key constraint or index on the exact ordered tuple.
6. New reference columns on dependent tables.
7. Dual-write of old and new reference tuples.
8. Backfill and verification of every dependent table.
9. New foreign keys referencing the candidate key created in step 5.
10. Application cutover.
11. Drop or repoint foreign keys that still depend on the old primary or unique
   key. If any must remain temporarily, preserve the old key as an alternate
   unique constraint.
12. Primary-key replacement using the explicit operation below.
13. Cleanup of old columns and alternate keys in later migrations after no
    dependency remains.

```text
new candidate columns + write invariant for each
  -> backfill + prove tuple non-null and unique
  -> unique candidate key on the exact new tuple
  -> new reference columns on children + dual-write old/new tuples
  -> backfill + verify every child
  -> new foreign keys -> application cutover
  -> primaryKey().replace(...) (+ dropIdentityFrom)
  -> drop old columns and alternate keys in a later migration
```

The final constraint operation is explicit:

```ts
table("orders").primaryKey().replace({
  expectedColumns: ["id"],
  columns: ["tenant_id", "order_id"],
  dropIdentityFrom: ["id"],
});
```

For an existing table with no primary key, use `.add({ columns })`. Removing a
primary key uses `.drop({ expectedColumns })`. `expectedColumns` is a drift
precondition, not an instruction to discover the key from live state.

These operations do not add columns, generate values, backfill rows, create
candidate uniqueness, or migrate foreign keys. `dropIdentityFrom` is the one
explicit generation transition they may perform. Omit it when the old columns
are supplied values or use ordinary defaults that can remain after the key
change.

Replace or drop refuses an identity or `autoIncrement()` column that would no
longer satisfy its target contract unless that column appears in
`dropIdentityFrom`. On MySQL, removal of `AUTO_INCREMENT` and replacement of the
key occur in the same table alteration. On SQLite, the rebuild turns the old
`INTEGER PRIMARY KEY` column into an ordinary integer and reconciles its
`sqlite_sequence` state. PostgreSQL drops the identity facet transactionally.

The operation performs only the final constraint and declared generation change
after validating all prerequisites. Apply inspects inbound foreign keys and
refuses any action that would remove their only valid referenced key unless an
exact alternate unique key already exists. PostgreSQL uses transactional
constraint DDL and may reuse a compatible unique index. MySQL combines drop and
add in one `ALTER TABLE`. For SQLite, apply disables foreign-key enforcement
before beginning the rebuild transaction, creates and copies the replacement,
drops and renames inside the transaction, recreates indexes and triggers, runs
`foreign_key_check`, and commits only when it is clean. It restores foreign-key
enforcement after the transaction ends, including after rollback. The initial
implementation must not expose a misleading one-call `changeIdType()` operation.

## Minimal Rust model

The engine needs only a few new semantic concepts. Serialization annotations,
field naming, and decoder mechanics belong in the implementation, not in this
high-level design.

```rust
pub enum ValueFormat {
    TypeId { prefix: String },
    Ulid,
}

pub enum PerRowGenerator {
    UuidV4,
    UuidV7,
    TypeId { prefix: String },
    Ulid,
}

pub enum CursorStability {
    GuardUpdates,
    ExternalInvariant { name: String },
}

pub enum PrimaryKeyAction {
    Add { columns: Vec<String> },
    Replace {
        expected_columns: Vec<String>,
        columns: Vec<String>,
        drop_identity_from: Vec<String>,
    },
    Drop {
        expected_columns: Vec<String>,
        drop_identity_from: Vec<String>,
    },
}
```

Physical storage remains in the existing column type. TypeID and ULID add only
optional stored-format metadata. Database UUID defaults remain ordinary
expression variants, while `PerRowGenerator` is accepted only by migration
backfills. Composite keys and references remain ordered column vectors rather
than a new scalar ID type. Exact 64-bit migration values and cursor checkpoints
reuse the migration scalar model.

The IR must preserve these distinctions and reject malformed artifacts, but its
exact JSON and Serde representation is an implementation decision covered by
contract tests. It is not part of the user-facing ID design.

## Policy behavior

Host policy may:

- require an ID family;
- inject an ID when the author omitted one;
- reject an incompatible ID;
- reserve stored prefixes;
- require supplied values rather than database generation for platform-managed
  tables.

Host policy must not reinterpret an authored UUID as text, discard its default,
or change its generator. A declared ID has the same meaning before and after
policy resolution.

If policy injects a system ID, the resolved plan and preview must show the exact
injected storage, format, executable generation, primary key, and zero-migrate
wire representation.

## Pre-release transition

The current surface contains correctness hazards:

- `t.id()` hides storage, generation, nullability, and key semantics behind a
  single shortcut.
- `t.id({ prefix })` is sometimes a UUID declaration and sometimes a declaration
  for an injected text ID.
- the existing internal typed ID uses 22-character Base62 UUIDv7, not TypeID;
- `t.ref()` always becomes text;
- identity metadata is not fully introspected for drift.

Because zero-migrate is pre-release, make these corrections in place. Do not
change package versions or `CURRENT_IR_VERSION`. Keep one current recorder, one
IR shape, one lowering path, and one checksum scheme.

Transition steps:

1. Add exact `UuidV4` and `UuidV7` expression variants to the current IR.
2. Remove `t.id()` and `t.id({ prefix })` from the public API. Migrate repository
   source to explicit `t.*` composition or `ids.typeId({ prefix })` according to
   the intended stored format.
3. Make `genRandomUuid()` a deprecated source alias that records `UuidV4`.
4. Replace the current MySQL UUIDv1 and SQLite 32-hex lowering with exact
   canonical UUIDv4 generation.
5. Keep the platform's internal typed-ID format named separately from TypeID.
6. Remove `t.ref()` and migrate source to explicitly typed `.references()`.
7. Add TypeID, ULID, per-row generation, and `int64` fields directly to the
   current IR and generated TypeScript IR definitions.
8. Add MySQL and SQLite lowering, validation, introspection, and drift detection
   for table-level composite foreign keys.
9. Replace `cursorColumn` with canonical `cursorColumns` IR, explicit cursor
   stability, and typed tuple progress checkpoints. Migrate repository fixtures
   and development progress state directly.
10. Add `AlterPrimaryKey` IR and target planners for explicit add, replace, and
    drop operations, including declared generated-integer transitions.
11. Update policy so it validates or injects a declared shape without
   reinterpreting authored columns.
12. Add identity, default, format, and reference drift introspection before
   advertising complete drift detection.

The SDK, engine, generated IR types, fixtures, and documentation change together.
Committed migration artifacts and checksums are regenerated as part of the
breaking pre-release update. Existing development databases must be recreated or
explicitly rebaselined; the engine must never silently ignore a checksum
mismatch.

## Final recommendation

Adopt a layered API:

```ts
id: t.bigInt().primaryKey().autoIncrement()
id: t.uuid().primaryKey().default(uuidV4())
id: t.uuid().primaryKey() // an external writer supplies the UUID
id: ids.typeId({ prefix: "user" }).primaryKey()
id: ids.ulid().primaryKey()
id: t.bigInt().primaryKey() // externally allocated integer
id: t.text().primaryKey() // assigned natural, external, or opaque string
```

Composite identity stays table-level:

```ts
table("memberships").create({
  columns: {
    account_id: t.uuid().notNull(),
    organization_id: t.uuid().notNull(),
  },
  primaryKey: ["account_id", "organization_id"],
});
```

Every example states its storage, generation authority, and key constraint. The
API supports the long tail without inventing a helper for every algorithm, and
it prevents storage type, executable generation, key constraint, format, and
external application behavior from being confused again.
